# PayFast integration boundary

Current checkout captures first name, last name, mobile, email, merchant ID, pickup address, product IDs, item and option snapshots, quantities, total in ZAR cents, currency, fulfillment, a unique GoodKota order ID and the explicit `pay_on_collection` / `unpaid` state. `js/core/checkout.js` defines this browser order shape. Before placing an order, the browser rechecks live item availability, selected options and prices; the order builder also recomputes prices from that merchant's current menu and rejects stale or mixed cart data. The UI shows cents where relevant. These fields are a UI and order contract only; static browser storage is not a trusted payment or order database.

## Merchant onboarding in this build

Every merchant needs their own PayFast account. After GoodKota approves a listing, Merchant → Store guides an Individual trader or registered Business through PayFast's own sign-up and verification. The merchant returns to GoodKota with an eight-digit Merchant ID. GoodKota → Payments can mark these details checked or request an update, with a note. This is a browser-only demonstration state: it is not provider authorization, merchant identity verification or an activated payment connection. Passwords, bank account numbers and verification documents stay in PayFast's flow.

The sign-up link is a guided handoff to PayFast's official selector. An embedded account-creation flow would require a documented partner onboarding agreement or API from PayFast; no such capability is assumed here.

## Split agreement and settlement model

PayFast's public split documentation describes a primary account, a secondary receiving account and a custom checkout integration. It allows one receiving merchant per split transaction and uses ZAR cents for amounts. The GoodKota cart already restricts orders to one merchant. The PayFast support example describes a merchant primary account and platform secondary account; GoodKota must obtain written confirmation of the account direction for its agreement before selecting credentials or calculating commission. A split into PayFast balances is distinct from withdrawal to each party's bank account.

Confirm the split percentage or fixed fee, payment processing fee owner, rounding, cancellation and refund allocation, partial refunds, chargebacks, recipient approval, merchant account types and sandbox test accounts with PayFast. Persist the agreed split terms per merchant and the exact calculated split per payment attempt server-side. Do not trust a client-supplied split payload or Merchant ID. One merchant per order remains a prerequisite.

## Credential setup in this build

PayFast's hosted integration uses a Merchant ID, Merchant Key and optional Security Passphrase, with separate sandbox and live credentials. GoodKota office selects the operating store in Payments; each store has a separate provider configuration, ready for the agreed account topology. The screen calls the bundled Node server's `/api/admin/payfast/*` endpoints. A separate setup access token gates status, save and removal; credentials are encrypted with AES-256-GCM using `GOODKOTA_CONFIG_KEY` and saved outside the public web root. The browser receives only masked status and never persists the access code or provider credentials. The service worker skips all `/api/` requests. GitHub Pages has no such endpoints and cannot store or use credentials. Merchant-facing onboarding asks for an ID only; never ask merchants to type their PayFast secret into browser demo storage.

The setup token is a local infrastructure gate, not a substitute for production account authentication. The prototype server does not have an authoritative merchant registry; the setup token controls which store ID receives credentials. In production, replace it with authenticated admin authorization, a server-side merchant registry, HTTPS, a managed secret store, rotation and auditable access. Bind every payment attempt to the correct store and its provider account. Configured credentials alone do not enable checkout. Both sandbox and live remain `checkoutActive:false` until the server payment flow below is implemented and tested.

## Server flow to add before enabling online payment

1. Authenticate the customer, merchant and office roles and store the order and verified merchant payment configuration in a server database. Accept product IDs, option IDs and quantities from the browser. Reprice every item and option server-side, check availability, single-select preference groups and one-merchant cart rules, then create a durable order with a unique ID and `payment_status=pending`. Persist customer contact details under an appropriate privacy and retention policy.
2. On choosing PayFast, ask the server to create a payment attempt tied to that order. The server uses the checkout-initiating account's configured Merchant ID/Key and passphrase, an approved receiving account Merchant ID and server-calculated split in ZAR cents. Build the hosted checkout payload, including a unique `m_payment_id`, server-calculated total, provider `setup` split field, item name, customer fields, HTTPS `return_url`, `cancel_url` and public `notify_url`. PayFast's docs say the `setup` field is not included in the signature, which makes it especially important that only the server assembles the payment request and the resulting split is reconciled with provider records. Redirect the customer to PayFast's hosted checkout.
3. On the PayFast notification endpoint, validate the signature, origin, PayFast server confirmation and expected order amount, merchant and split against the stored attempt and provider records. Deduplicate notifications and update payment status atomically. Only a verified completed payment may move a PayFast order into the merchant's actionable queue.
4. A return URL is only a navigation event. Read the server's order status there; never mark an order paid because the browser returned. A cancelled attempt leaves the cart/order recoverable. Handle delayed, duplicate and out-of-order notifications and maintain an audit trail of payment attempts and status transitions.
5. Test with both primary and secondary sandbox accounts, a publicly reachable notification endpoint, merchant account eligibility, rounding, cancellations and partial refunds before switching to live credentials. Do not expose credentials, passphrase, signatures or customer details in static assets.

Suggested payment statuses: `unpaid` (pay on collection), `pending`, `paid`, `failed`, `cancelled`, `refunded`. The current `placeOrder` path writes `pay_on_collection` and `unpaid`; an online path must call the server and must not reuse the local order insertion as proof of payment. Merchant order acceptance for online payments should be gated by the server's verified payment state.

See `PAYFAST-SPLIT-DECISIONS.md` for the specific provider answers required before implementation. One GoodKota order may have multiple payment attempts, so a future attempt reference must be unique per attempt rather than reusing the order reference for every retry.
